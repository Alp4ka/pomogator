# Pomogator engineering guide

## Назначение
Pomogator — Telegram-бот и Mini App для защищённой публикации материалов о переезде. Notion является редакторским источником, PostgreSQL — единственным runtime-источником контента. Клиент никогда не обращается к Notion напрямую.

## Слои backend
- `domain`: бизнес-типы и инварианты. Не импортирует FastAPI API, aiogram long polling, SQLAlchemy или внешние SDK.
- `application`: сценарии и порты. Оркестрирует домен, транзакции и внешние интерфейсы.
- `infrastructure`: SQLAlchemy, Notion, платежи, очереди. Реализует порты application.
- `presentation`: HTTP API; Telegram handlers запускаются отдельным long polling процессом. Только проверка ввода, вызов сценария и формирование ответа.
- `frontend`: Mini App. Считает сервер единственным источником прав доступа.

Направление зависимостей: presentation/infrastructure → application → domain. Не помещайте бизнес-правила в handlers, ORM-модели или React-компоненты.

## Правила безопасности
- Платный контент блокируется в API; скрытие кнопки на клиенте не является защитой.
- Telegram `initData` всегда проверяется через HMAC и срок жизни. Telegram ID из тела запроса недоверенный.
- Секреты не коммитятся. `.env.example` содержит только пустые или демонстрационные значения.
- Внешние URL из Notion остаются внешними. Только распознанные Notion page URL превращаются во внутренние маршруты.
- Изображения скачиваются при sync, валидируются по MIME/размеру и выдаются авторизованным endpoint.
- HTML из Notion не хранится и не рендерится. Добавляйте новые блоки через безопасную JSON-схему и явный React renderer.

## Стиль и дополнение кода
- Python: зависимости и команды только через uv; type hints, async I/O, Ruff, mypy strict, функции до одного уровня ответственности. Публичные контракты тестируются.
- TypeScript: strict mode, без `any`, доступ к API через типизированный слой. UI учитывает loading/error/empty/locked состояния и тему Telegram.
- Новая интеграция начинается с Protocol в application/domain и отдельного адаптера infrastructure.
- Новая таблица или изменение столбца требует новой Alembic-миграции; уже применённые миграции не редактируются.
- Синхронизация и платежные callbacks должны быть идемпотентными. Любое изменение доступа сопровождается серверным тестом.
- Тесты: unit для домена, integration для БД/API, contract fixtures для Notion, E2E для ключевого пути пользователя.
